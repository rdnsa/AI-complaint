Laporan progress pengembangan · Kato Report

Situs staging dan enam checkpoint pengembangan

Kato Report adalah sistem pelaporan kondisi toilet kampus UPI Tasikmalaya. Mahasiswa melapor lewat QR, AI mengubah keluhan menjadi tiket kerja, dan penyelesaiannya dibuktikan dengan foto yang diperiksa AI. Dokumen ini menjelaskan bagaimana sistem itu dibangun dalam enam checkpoint, dan bagaimana setiap checkpoint bisa dicoba langsung di situs staging.

1. Ringkasan

Apa yang dibangun, dan bagaimana progresnya dilaporkan.

Masalah. Keluhan tentang toilet kampus jarang sampai ke petugas kebersihan. Mahasiswa tidak tahu harus melapor ke siapa, dan tidak ada cara untuk memastikan keluhannya ditindaklanjuti. Akibatnya masalah kecil dibiarkan sampai menjadi besar.

Solusi. Stiker QR di setiap lantai. Mahasiswa memindai QR dan menulis keluhan dengan bahasa sehari-hari. AI (DeepSeek) menggolongkan keluhan, menentukan prioritas, dan menyusun perintah kerja. Petugas menutup laporan dengan foto bukti yang diperiksa AI kedua (Google Gemini). Supervisor memantau semuanya lewat dashboard dan Chatbot AI.

Cara melaporkan progres. Sistem final ada di branch main. Riwayat pengembangannya dibagi menjadi enam checkpoint, masing-masing ditandai dengan tag git checkpoint-1 sampai checkpoint-6. Setiap checkpoint dijalankan sebagai aplikasi tersendiri di situs staging, sehingga siapa pun bisa mencoba sistem persis seperti pada tahap tersebut.

Untuk siapa saja yang ingin mencoba setiap checkpoint.

Langkah mencoba

  1. Buka /checkpoint, lalu pilih checkpoint yang ingin dicoba. Mulailah dari checkpoint 1 supaya perkembangannya terasa.
  2. Penanda "Checkpoint N/6 · ganti" di pojok kiri bawah menunjukkan checkpoint yang sedang aktif. Ketuk penanda itu untuk kembali ke hub.
  3. Ikuti skenario uji di bagian setiap checkpoint dalam dokumen ini.
  4. Untuk membandingkan dua checkpoint berdampingan, buka checkpoint kedua di jendela penyamaran atau browser lain.

Catatan keamanan. Admin123! adalah sandi bawaan dari migrasi database dan tercantum di repo publik. Sandi ini hanya boleh dipakai di staging. Di produksi (main) sandi itu wajib diganti.

Yang perlu diketahui penguji

  • Data setiap checkpoint terpisah. Laporan yang dikirim di checkpoint 2 tidak muncul di checkpoint 3, karena struktur database tiap checkpoint berbeda. Silakan mengirim laporan percobaan sebanyak yang diperlukan.
  • Login juga terpisah. Masuk di checkpoint 3 tidak membuat Anda ikut masuk di checkpoint 4.
  • Satu browser, satu checkpoint. Berpindah checkpoint di satu tab ikut memindahkan tab lain di browser yang sama.
  • Fitur AI memakai layanan sungguhan. Klasifikasi keluhan memakai DeepSeek, dan pemeriksaan foto (checkpoint 5–6) memakai Gemini. Kalau layanan itu sedang sibuk, laporan tetap tersimpan dan hasil AI bisa dianalisis ulang.
  • Ringkasan harian otomatis (pukul 17.00 WIB) hanya berjalan di checkpoint terbaru. Di checkpoint lama, ringkasan tetap bisa dibuat manual dari dashboard.

3. Arsitektur staging (teknis)

Bagaimana enam versi aplikasi berjalan bersamaan di satu domain tanpa mengubah kode aplikasinya.

Model branch dan tag

  • main berisi sistem final, dan dari branch inilah produksi di-deploy.
  • Tag checkpoint-1 sampai checkpoint-6 menandai commit di main yang menjadi batas setiap checkpoint: dd9c91a, feb7e49, 2e18c48, d2e7d72, e44958b, dan defb699.
  • staging dimulai dari checkpoint-1. Setiap kali melapor, tag berikutnya di-merge dengan git merge --no-ff checkpoint-N. Arahnya selalu satu: main ke staging, tidak pernah sebaliknya.
  • File khusus staging tidak pernah ada di main, sehingga merge tidak pernah konflik. File-file itu adalah STAGING.md, staging.config.json, scripts/staging.mjs, dan folder staging/ (router.mjs, checkpoints.mjs, journey.mjs, docs/). Setelah checkpoint 6, isi staging sama dengan main ditambah file-file ini.

Topologi

Router (staging/router.mjs)

Aplikasi di setiap checkpoint memakai alamat absolut seperti /api/… dan /lapor/…, sehingga tidak bisa dipasang di bawah awalan seperti /checkpoint3/ tanpa mengubah kode lamanya. Router menyelesaikan masalah itu tanpa menyentuh kode aplikasi:

  1. /checkpoint menyajikan halaman hub statis dari binding ASSETS.
  2. /checkpointN[/jalur] memasang cookie kato_checkpoint=N (30 hari, SameSite=Lax, Secure) lalu mengalihkan ke /jalur. Checkpoint yang belum dilaporkan dialihkan ke hub.
  3. Permintaan lain diteruskan ke Worker ai-complaint-staging-cpN lewat service binding CPn, sesuai cookie. Kalau cookie tidak ada, yang dipakai checkpoint terbaru. URL permintaan tidak diubah, jadi aplikasi melihat domain staging sebagai domainnya sendiri.
  4. Cookie aplikasi dipisah per checkpoint. Setiap Set-Cookie dari aplikasi disimpan dengan awalan cpN_, misalnya cp1_sesi_petugas. Saat meneruskan permintaan, router hanya mengirim cookie berawalan checkpoint aktif dan mengembalikan namanya ke nama aslinya. Tanpa pemisahan ini, sesi dari satu checkpoint bisa diterima checkpoint lain yang memakai AUTH_SECRET sama, padahal id pengguna yang sama di database lain bisa berarti orang lain.
  5. Pada respons HTML, HTMLRewriter menyisipkan penanda "Checkpoint N/6 · ganti" di akhir <body>.

Worker, database, dan penyimpanan

Sumber dayaNamaKeterangan

Skrip deploy (scripts/staging.mjs)

Skrip ini tidak pernah mengubah wrangler.jsonc milik main. Sebagai gantinya, skrip membaca file itu dan menulis konfigurasi sementara wrangler.staging.jsonc yang dihapus lagi setelah selesai. Urutan kerja node scripts/staging.mjs:

  1. Menentukan checkpoint terbaru, yaitu tag terakhir yang commit-nya sudah menjadi leluhur HEAD (git merge-base --is-ancestor).
  2. Mencari database D1 checkpoint itu, atau membuatnya (wrangler d1 create --update-config=false) kalau belum ada.
  3. Menjalankan migrasi. Untuk database baru, atau dengan argumen seed, skrip juga mengisi data toilet dari seed/toilets.sql.
  4. Men-deploy Worker checkpoint dengan nama, database, dan bucket staging, lalu mengirim secret dari .dev.vars.
  5. Melepas cron dari Worker checkpoint sebelumnya.
  6. Membuat halaman hub dan dokumentasi (staging/journey.mjs), lalu men-deploy router dengan service binding ke semua checkpoint yang sudah dilaporkan.

Secret

Secret Cloudflare tidak bisa dibaca kembali, jadi nilainya diambil dari .dev.vars lokal, yang tidak ikut di-commit. Secret yang dipakai adalah LLM_API_KEY, VISION_API_KEY, AUTH_SECRET, dan PETUGAS_PASSWORD (khusus checkpoint 1–2). Sejak checkpoint 6, LLM_API_KEY dan VISION_API_KEY boleh berisi beberapa key yang dipisah koma. Kode checkpoint yang lebih lama akan membaca daftar itu sebagai satu key yang tidak valid, jadi skrip memeriksa kodenya dulu: kalau fungsi splitKeys belum ada, hanya key pertama yang dikirim.

Penjelasan umum

Masalah yang dijawab. Keluhan toilet tidak punya saluran. Checkpoint ini membangun alur paling dasar: mahasiswa bisa melapor dalam hitungan detik, dan petugas menerima laporan dalam bentuk yang langsung bisa dikerjakan.

Yang bisa dilakukan

  • Mahasiswa memindai QR di pintu WC, menulis keluhan dengan bahasa sehari-hari (bahasa gaul juga dipahami), melampirkan foto kalau mau, lalu mengirim. Konfirmasi langsung muncul.
  • AI menentukan jenis masalah, prioritas, ringkasan yang sopan, dan perintah kerja.
  • Petugas masuk dengan satu sandi bersama, melihat laporan dengan yang paling mendesak di atas, lalu mengubah statusnya dari baru ke diproses ke selesai.
  • Pimpinan menerima ringkasan harian otomatis setiap pukul 17.00 WIB.

Contoh hasil AI

"WC lantai 2 bau banget, lantainya becek, sama sabunnya habis."

  • Prioritas: tinggi
  • Masalah: bau, genangan air, perlengkapan habis
  • Perintah: keringkan lantai lebih dulu karena berisiko membuat orang terpeleset, lalu bersihkan sumber bau dan isi ulang sabun.

Skenario uji

  1. Buka /checkpoint1/lapor/A-1-PRIA. Formulir sudah mengetahui WC mana yang dimaksud.
  2. Tulis "airnya nggenang parah, kloset yg pojok mampet", lalu kirim. Di halaman konfirmasi, tunggu sampai kategori dan prioritas muncul. Hasil yang diharapkan: kerusakan dan genangan air, prioritas tinggi.
  3. Buka /petugas, masuk dengan nama bebas dan sandi bersama, lalu ubah status laporan tadi. Coba juga tombol analisis ulang.
  4. Di dashboard, buat ringkasan harian secara manual.

Yang belum ada: daftar lokasi masih data contoh, pelapor tidak bisa melacak laporannya setelah menutup halaman, dan semua petugas memakai satu sandi.

Penjelasan teknis

Fondasi

  • Stack: TypeScript di Cloudflare Workers dengan Hono. Database D1 (SQLite), penyimpanan foto R2, dan frontend React + Vite + Tailwind. Frontend dan API ada di satu Worker, sehingga tidak perlu CORS dan cukup sekali deploy. Aset statis disajikan lewat binding ASSETS dengan run_worker_first: ["/api/*"] dan fallback SPA.
  • Analisis asinkron: POST /api/reports langsung menyimpan laporan dan menjawab. Analisis LLM dijalankan lewat ctx.waitUntil() setelah respons terkirim, sementara halaman konfirmasi melakukan polling.
  • Ketahanan: kalau LLM gagal, laporan ditandai ai_status = 'gagal' beserta pesan errornya. Laporan itu tetap tampil dan bisa dianalisis ulang lewat POST /api/reports/:id/analisa-ulang. Latensi setiap panggilan dicatat di ai_ms.
  • Validasi keluaran LLM: JSON dari DeepSeek (response_format: json_object, temperatur rendah, contoh few-shot) divalidasi dengan Zod, lalu dipaksa masuk ke enum yang dikenal database. Kategori asing dibuang, dan prioritas yang tidak dikenal menjadi sedang.
  • Foto lewat Worker: GET /api/uploads/:key membaca objek langsung dari R2, dibatasi hanya untuk prefiks laporan/, dan meneruskan ETag. Alasannya, sebagian ISP di Indonesia membajak DNS untuk *.r2.dev, sehingga foto gagal dimuat di jaringan kampus.
  • Build otomatis: build.command di wrangler.jsonc membangun frontend sebelum deploy, supaya wrangler deploy berjalan sendiri, termasuk di Workers Builds.
  • Cron 0 10 * * * (17.00 WIB) menyusun daily_summaries. Ringkasan juga bisa dibuat manual lewat POST /api/summary/generate.

Database: migrasi 0001_init.sql

Tabel toilets (satu baris per WC fisik, id seperti A-2-PRIA di-encode ke QR), reports (keluhan, status, hasil AI: kategori, prioritas, ringkasan, rekomendasi, ai_status), dan daily_summaries, ditambah empat indeks untuk urutan dashboard.

Penjelasan umum

Masalah yang dijawab. Satu QR per WC berarti terlalu banyak stiker yang harus dicetak dan dirawat, dan daftar lokasinya belum mencerminkan kampus. Selain itu, laporan yang sudah dikirim seolah menghilang: pelapor maupun orang lain tidak bisa melihat tindak lanjutnya.

Yang berubah

  • Satu QR per lantai. Pelapor memilih sendiri WC pria, wanita, atau disabilitas. Totalnya 13 stiker untuk 6 gedung yang punya toilet.
  • Gedung UPI Kampus Tasikmalaya yang asli, dengan peta kampus di beranda sebagai cadangan kalau QR rusak.
  • Identitas visual kampus (maroon, oranye bata, krem) dan pilihan bahasa Indonesia/Inggris.

Transparansi

  • Lacak laporan: garis waktu diterima, dikerjakan, selesai, dan daftar "Laporan saya" di beranda.
  • Papan laporan publik /laporan: semua laporan dan statusnya, tanpa login.
  • Hapus spam oleh petugas, karena papannya kini terbuka untuk umum.

Skenario uji

  1. Buka /checkpoint2/lapor/A-1, pilih jenis WC, lalu kirim keluhan.
  2. Kembali ke beranda. Laporan tadi muncul di "Laporan saya" beserta statusnya.
  3. Buka /laporan. Yang tampil hanya ringkasan AI, tanpa teks asli maupun foto pelapor.
  4. Masuk sebagai petugas, ubah status, lalu lihat garis waktu di halaman konfirmasi ikut berubah.
  5. Ganti bahasa ke EN dari bagian atas halaman.
Penjelasan teknis
  • Migrasi 0002_gedung_upi.sql: tabel gedung berisi sepuluh gedung, dan toilets mendapat gedung_kode. Kolom gedung dan nama dihapus, dan ditambah indeks lokasi. Id lokasi QR berformat <kode gedung>-<lantai>, misalnya A-1.
  • Seed yang aman dijalankan ulang: semua WC dinonaktifkan dulu, lalu yang terdaftar diaktifkan kembali. Versi sebelumnya menghapus isi tabel dan gagal karena foreign key begitu ada laporan. Lantai yang terdaftar: A 1–3, B 1, C 1–5, G 1, H 1, dan I 1–2. Gedung D, E, F, dan J disiapkan sebagai komentar.
  • Pelacakan tetap anonim: id laporan (UUID acak) disimpan di localStorage. GET /api/reports/ringkas mengambil status banyak laporan dalam satu permintaan. Halaman konfirmasi menyegarkan diri dengan cepat selama analisis berjalan, melambat setelahnya, dan berhenti saat tab tidak terlihat.
  • Papan publik GET /api/reports/publik sengaja tidak menyertakan teks asli, foto pelapor, maupun nama petugas. Mengubah, menganalisis ulang, dan menghapus tetap membutuhkan sesi petugas.
  • DELETE /api/reports/:id juga menghapus foto di R2 agar tidak meninggalkan berkas yatim.
  • i18n memakai kamus sendiri tanpa pustaka. Hasil LLM tetap berbahasa Indonesia karena pembacanya petugas.

+ endpoint: GET /api/lokasi, GET /api/lokasi/:id, GET /api/reports/publik, GET /api/reports/ringkas, DELETE /api/reports/:id. − endpoint: GET /api/toilets, GET /api/toilets/:id.

Penjelasan umum

Masalah yang dijawab. Laporan bisa ditutup dengan satu klik tanpa bukti. Karena semua petugas memakai satu sandi, tidak bisa diketahui siapa melakukan apa, dan mencabut akses satu orang berarti mengganti sandi semua orang.

Akuntabilitas

  • Foto keadaan wajib dilampirkan pelapor.
  • Selesai berarti ada foto bukti. Tanpa foto bukti, laporan tidak bisa ditutup. Foto bukti tampil di papan publik.
  • Catatan aktivitas merekam semua kejadian, termasuk laporan yang dihapus.
  • Grafik: laporan masuk dan selesai per hari, prioritas, kategori, per gedung, dan rata-rata waktu penyelesaian.

Akun

  • Akun pribadi dengan peran admin, petugas, atau pelapor.
  • Admin mengelola akun petugas dan menonaktifkannya kalau perlu.
  • Mahasiswa boleh mendaftar untuk masuk papan peringkat. Melapor tanpa akun tetap bisa.

Skenario uji

  1. Buka /checkpoint3/daftar, buat akun pelapor, lalu kirim laporan dengan foto. Cek /peringkat.
  2. Masuk di /masuk sebagai admin / Admin123!, lalu buat satu akun petugas di tab Pengguna.
  3. Masuk sebagai petugas itu dan coba menandai laporan selesai tanpa foto. Hasil yang diharapkan: ditolak. Unggah foto bukti, dan laporan pun selesai.
  4. Kembali sebagai admin, lalu buka tab Grafik dan Aktivitas.
Penjelasan teknis
  • Migrasi 0003_bukti_dan_aktivitas.sql: reports.foto_selesai_key dan tabel aktivitas dengan tiga indeks. Tabel aktivitas sengaja tanpa foreign key ke reports, karena justru laporan yang dihapus yang paling perlu terlacak. Isinya disalin ke catatan sebelum baris aslinya dihapus.
  • Migrasi 0004_pengguna.sql: tabel pengguna (peran admin/petugas/pelapor), reports.pelapor_id, dan akun admin bawaan.
  • Aturan wajib foto dijaga di server, bukan hanya disembunyikan di antarmuka, sehingga tidak bisa diakali lewat klien lain.
  • Kata sandi di-hash dengan PBKDF2-SHA256, 100.000 iterasi, salt per pengguna, lewat WebCrypto. Bcrypt dan argon2 tidak tersedia di runtime Workers tanpa WebAssembly tambahan. Pesan galat untuk "akun tidak ada" dan "sandi salah" dibuat identik untuk mencegah enumerasi username. Admin tidak bisa menonaktifkan akunnya sendiri. Secret PETUGAS_PASSWORD tidak dipakai lagi.
  • Palet grafik dipilih lewat validator: rentang terang, ambang chroma, keterpisahan untuk buta warna, dan kontras terhadap latar.

Penjelasan umum

Masalah yang dijawab. Fitur makin banyak, tetapi kode server bercampur jadi satu, sehingga setiap perubahan berisiko merusak bagian lain. Grafik juga baru menjawab "berapa banyak", padahal pimpinan butuh jawaban "kapan", "di mana", dan "apakah prioritas AI berguna".

Yang terasa oleh pengguna

  • "Laporan saya" ikut akun, jadi bisa dilihat dari perangkat mana pun.
  • Angka utama dengan tren dan perbandingan dengan periode sebelumnya.
  • Peta panas hari × jam sebagai dasar jadwal ronda.
  • Matriks gedung × jenis masalah.
  • Waktu penyelesaian per prioritas, untuk menguji apakah prioritas AI memang bermanfaat.

Dokumen

  • Panduan umum tanpa istilah teknis, untuk staf dan pimpinan kampus.
  • Dokumentasi teknis untuk penilai.
  • Keduanya ditulis dalam HTML dengan print stylesheet, sehingga satu sumber menghasilkan halaman web dan PDF.

Skenario uji

  1. Buka /checkpoint4/masuk dan masuk sebagai admin. Kirim beberapa laporan dengan prioritas berbeda, lalu selesaikan sebagian.
  2. Buka tab Grafik dan amati deretan angka utama, peta panas, matriks, dan waktu penyelesaian per prioritas.
  3. Daftar sebagai pelapor, kirim laporan, lalu masuk dengan akun yang sama dari browser lain. "Laporan saya" tetap muncul.
Penjelasan teknis
  • Arsitektur berlapis. Sebelumnya 37 dari 43 pernyataan SQL berada di dalam route handler. Sekarang ada lima lapisan dengan ketergantungan yang hanya mengarah ke dalam:
    • domain/: kosakata dan aturan bisnis, tanpa import Hono, D1, maupun R2
    • repositories/: semua SQL, satu file per agregat
    • services/: use case, tanpa Hono
    • adapters/: LLM, R2, hashing, sesi, dan jam
    • routes/: parsing, validasi, delegasi, dan format

Penjelasan umum

AI pemeriksa foto

Setiap foto bukti dinilai: benar toilet? sudah bersih? Kalau belum, foto ditolak beserta alasannya, laporan tetap terbuka, dan petugas diminta membersihkan lagi.

  • Ditolak: "Lantai masih basah dan ada tisu bekas."
  • Diterima: "Kloset dan lantai terlihat bersih tanpa sampah."

Chatbot AI dan lainnya

  • Pertanyaan biasa seperti "Gedung mana yang paling banyak laporan 30 hari terakhir?" dijawab dengan angka dari data sungguhan.
  • Foto yang lolos pemeriksaan diberi tanda diverifikasi AI di papan publik.
  • Mode gelap, ikon mata di kolom sandi, dan logo baru.

Skenario uji

  1. Di /checkpoint5, kirim laporan, lalu masuk sebagai admin (atau petugas yang dibuat admin).

  3. Ajukan pertanyaan ke Chatbot AI di beranda atau di dashboard.
  4. Coba sakelar terang/gelap.
Penjelasan teknis
  • Dua model AI. DeepSeek tidak bisa melihat gambar, jadi foto dinilai oleh model vision terpisah lewat endpoint yang kompatibel dengan OpenAI: VISION_BASE_URL Gemini dengan VISION_MODEL = gemini-3.6-flash. VISION_API_KEY jatuh ke LLM_API_KEY kalau tidak diisi.

Kuotanya 50 pertanyaan per hari untuk seluruh kampus dan 20 per IP tanpa akun. Nama petugas hanya diberikan kepada pengguna yang login.

5. Operasional staging

Untuk pengembang yang merawat situs staging.

Persiapan sekali saja

npx wrangler r2 bucket create kato-staging
npx wrangler d1 create kato-staging --update-config=false   # isi database_id di staging.config.json
cp .dev.vars.example .dev.vars                                 # isi LLM_API_KEY, VISION_API_KEY, AUTH_SECRET, PETUGAS_PASSWORD

staging.config.json berisi nama Worker router, nama dan id database checkpoint 1, nama bucket, dan domain (opsional). Kalau domain diisi, domainnya harus berupa zone di akun Cloudflare yang sama.

Naik ke checkpoint berikutnya

git switch staging
git merge --no-ff checkpoint-N -m "Checkpoint N"
node scripts/staging.mjs          # database dibuat dan diisi otomatis bila baru
git push origin staging

Perintah lain

PerintahFungsi
node scripts/staging.mjs seedDeploy, sekaligus mengisi ulang data toilet di database checkpoint terbaru (aman dijalankan berulang)
node scripts/staging.mjs secretsMengirim ulang secret dari .dev.vars ke Worker checkpoint terbaru
node scripts/staging.mjs configHanya menulis wrangler.staging.jsonc untuk diperiksa

Masalah yang pernah terjadi

GejalaPenyebabPenanganan
Sesaat setelah deploy, checkpoint baru menjawab "Endpoint tidak ditemukan" atau penanda menunjukkan nomor lamaRouter versi baru belum menyebar ke semua lokasi Cloudflare, jadi sebagian permintaan masih memakai daftar checkpoint lamaTunggu sekitar satu menit

  • D1: 10 database per akun. Staging memakai 6, dan akun ini sudah terisi 10.
  • Cron: 5 per akun. Staging hanya memakai 1, di checkpoint terbaru.

npx wrangler delete --name ai-complaint-staging

npx wrangler d1 delete kato-staging
